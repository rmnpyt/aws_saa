## The Problem: Hardcoded Credentials

One of the most common security vulnerabilities in applications is hardcoded credentials in source code or configuration files:

```python
# BAD — never do this
db_password = "MyDBPassword123!"  # in source code
```

If this code is pushed to a public repository, attackers immediately have your database password.

## AWS Secrets Manager

**Secrets Manager** is the primary service for storing, managing, and automatically rotating secrets.

**What it stores:**
- Database credentials (RDS, Redshift, DocumentDB)
- API keys and tokens
- OAuth secrets
- Any text up to 64KB

**Key features:**

| Feature | Details |
|---|---|
| **Automatic rotation** | Built-in rotation for RDS, Redshift, DocumentDB. Rotation uses Lambda to update the secret and the database simultaneously. |
| **KMS encryption** | All secrets are encrypted with KMS |
| **Fine-grained access** | IAM policies control who can access which secrets |
| **Cross-account access** | Resource-based policy allows other accounts to read secrets |
| **Versioning** | Multiple versions of a secret (AWSCURRENT, AWSPENDING, AWSPREVIOUS) |

**Application usage:**
```python
import boto3
import json

client = boto3.client('secretsmanager')
secret = client.get_secret_value(SecretId='prod/myapp/db')
credentials = json.loads(secret['SecretString'])
# Use credentials['username'] and credentials['password']
```

**Automatic rotation process:**
1. Secret is about to expire
2. Lambda function is invoked
3. Lambda creates a new password in the database
4. Lambda stores the new password in Secrets Manager (AWSPENDING)
5. Lambda tests the new credentials
6. Lambda sets the new credentials as AWSCURRENT

<ExamTip>
When a question asks about automatic credential rotation for a database, the answer is **Secrets Manager**. When it asks about storing configuration values (non-sensitive), use **SSM Parameter Store**.
</ExamTip>

## AWS Systems Manager Parameter Store

**SSM Parameter Store** is a free (standard tier) configuration and secret storage service.

| Type | Description | Cost |
|---|---|---|
| **Standard** | Up to 10,000 parameters, no KMS cost for String/StringList, no additional charge | Free |
| **Advanced** | Unlimited parameters, up to 8KB per parameter, policies (expiration, notification) | $0.05/parameter/month |

**Parameter types:**
- **String**: Plain text (config values, environment names)
- **StringList**: Comma-separated values
- **SecureString**: Encrypted with KMS (use for passwords)

## Best Practices

1. **Never put credentials in code or environment variables** — use Secrets Manager or Parameter Store
2. **Use IAM roles** for applications to access secrets (no access keys needed)
3. **Enable rotation** for all database passwords
4. **Least privilege**: Each app should only access its own secrets
5. **Reference by name, not ARN**: Use the secret name with stage tags for portability

## IAM Identity Center and Federated Access (Brief)

Beyond Secrets Manager and Parameter Store, AWS provides:

- **IAM Identity Center (SSO)**: Centralized access management for humans across multiple accounts. Integrates with external IdPs (Okta, Azure AD).
- **AWS STS** (covered in IAM Roles lesson): Issues temporary credentials that expire — avoiding the need to store credentials at all.

## Summary

- **Secrets Manager**: Database passwords, API keys that need automatic rotation. More expensive but more powerful.
- **Parameter Store**: Configuration values, non-rotating secrets. Free for standard use.
- Both encrypt with KMS; both are accessed via IAM roles (not hardcoded credentials)
- Never hardcode credentials — always retrieve at runtime from Secrets Manager or Parameter Store
